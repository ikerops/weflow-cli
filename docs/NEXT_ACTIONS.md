# WeFlow CLI 下一阶段行动建议

> 编写日期：2026-10-14
> 依据：本地仓库 `package.json` 的 1.11.1 版本、截至本次梳理的提交与工作区状态。
> 用途：把近期改进方向拆成可以独立评审、实现和验收的任务。项目现状以 [PROJECT_STATE.md](PROJECT_STATE.md)、技术取舍以 [DECISIONS.md](DECISIONS.md) 为准。

## 建议结论

下一阶段应先完成三个“收口”任务：

1. 让历史文章回填与日报共用缓存的行为可控、可验证，尤其补上强制重新抓取的入口。
2. 统一不同导出格式的媒体状态语义，并补上导出失败和跨环境的验证证据。
3. 分批补齐 CLI 在 `--json` 模式下的运行时错误结构，保持机器调用结果稳定。

这三项都能建立在现有实现上，不需要引入新的数据处理架构。同步游标、MCP 扩面、资料包和更复杂的 AI 功能可在上述边界稳定后，根据实际集成需求推进。

## 当前基线

- 本地代码版本为 `1.11.1`。最近一批提交完成了 Markdown 连图、文档本体导出和文档导出的多项边界修复。
- 本次读取时，本地 `master` 比 `origin/master` 多 11 个提交；工作区中 `scripts/backfill_articles.py` 和 `test/backfill_articles_test.py` 有未提交改动。它们正在让历史回填复用日报正文缓存，本文件将这部分视为进行中的工作，不把它描述为已发布功能。
- HTML 导出已有媒体覆盖报告；Markdown 和 JSON/TXT/Excel 的媒体导出复用同一份清单。文件本体导出目前只有本机实测记录，Issue #11 尚待报告者确认及其他环境验证。
- `sync run/status/verify` 和本地同步状态契约已经存在，但稳定游标尚未作为对外能力承诺。
- 项目已记录扩展边界：代码扩展在仓库内完成；外部程序通过 CLI、JSON 或 MCP 接入。近期不建议增加进程内插件加载器。

## P0：完成正在进行的缓存衔接

**已完成（2026-10-14）**，验收的六类行为各有测试（命中不联网 / 未命中去抓 / 成功写缓存 / 失败不写 /
强制重抓刷新旧缓存 / 重抓失败不动旧缓存 / 缓存不可写不影响这一篇 / 并发下标不错位），关键两条做过变异检查。
落地的几处与本节设想不同的地方：回填与日报**共用同一条缓存**（`fetch_article_cached`，成功才写）；
`--no-fetch-cache` 两边同名同义；`--refresh` 的帮助写明它只管"做哪些天"。另外**多做了一个标记**：
抓取失败与"正文本来就短"从此分开记（`.articles.json` 的 `fetchFailed`，那天判为没做完、重跑只重试失败的篇）——
它直接对应本节验收里"失败后重跑可继续补齐，不会将部分日期或部分文章误标为完整"那一条。
判据与代价写在 D-108；顺带量到一件事：**接力是部分的**——日报对每篇有 url 的都抓正文，回填只抓"正文过短"的，
2026-10-13 那天 485 篇里只有 145 篇进了缓存（详见 D-108，未做显式预取开关）。

### 目标

使回填和日报共享正文缓存后，用户仍能明确选择复用缓存或重新抓取；重跑行为有测试保护，不会因旧缓存而悄悄使用过期正文。

### 建议工作

- 为历史回填增加显式的缓存控制选项，例如允许用户绕过已有缓存重新抓取；参数名称和交互方式应与日报已有的 `--no-fetch-cache` 保持一致或清楚说明差别。
- 明确 `--refresh` 的语义：它目前用于重做已回填日期，不应让用户误以为它必定重新请求文章正文。
- 覆盖缓存命中、缓存未命中、抓取成功、抓取失败、强制重抓及并发抓取的行为。
- 继续只缓存非空成功正文；缓存不可写时回填仍应按现有约定完成，不因缓存辅助功能导致整批失败。
- 确认文档中所述的缓存目录、请求节流和“日报生成可复用历史正文”与代码一致。

### 验收标准

- 默认回填会复用有效缓存，缓存命中时不访问网络。
- 用户显式选择重抓时，即使已有缓存也会访问正文来源，并以成功结果更新缓存。
- 抓取失败不会覆盖已有的有效缓存；没有旧缓存时，失败也不会生成空缓存文件。
- 失败后重跑可继续补齐，不会将部分日期或部分文章误标为完整。
- `test/backfill_articles_test.py` 和日报缓存相关测试覆盖以上行为；Python 脚本的参数帮助与实际行为一致。

### 需要注意

缓存只代表“曾成功抓到的正文”，不代表正文永远是最新版本。刷新入口应明确，而不应通过改变默认行为造成额外请求。

## P1：统一导出媒体状态与验证口径

**基本完成（2026-10-14）**，**只差本节最后那条"第二台设备/另一个账号的验收记录"**（依赖外部环境，做不了）。
已落地的：统一词汇（报告答"源数据里能不能定位"→ `found`/`missing`；清单与 CLI JSON 答"有没有落进导出目录"
→ `written`/`copied`/`unavailable`，此后没有哪个词承担两种意思）；`manifest.documents` 的 `exported` 改名为
`written`（此前与报告的 `exported` 同形不同义，拷贝失败时会让"已导出"变成假话）；三种格式（html / md /
`--media`）的机器可读摘要收成**一个函数** `media_json_summary`，因此不会再各说各话，且报告文件名三处都有
（此前只有 HTML 那条给）；回归测试覆盖"拷贝失败"（报告说 `found`、清单说 `unavailable`）、"重复运行"
（`written` 与 `copied` 分开，第二遍不误报 0）、"局部范围不吃掉宽范围的清单"（合并式写入），并断言摘要
**不含本机绝对路径**。仍未做：`ranges`（窄/宽）之外的状态读取兼容性只按现有 v1/v2 读取路径验过。

### 目标

让 HTML 报告、Markdown 清单及其他格式引用的媒体状态表达同一事实；用户可以区分“本地未找到”“已找到但未成功写出”和“已写入导出目录”。

### 建议工作

- 盘点 `weflow-media-report/v1` 与 `weflow-media-manifest/v2` 中的状态、计数和含义，尤其核对文档文件的 `exported`、`found` 与实际写入结果。
- 选定统一语义：媒体是否可在源数据中定位、是否成功写入资产目录、是否仅在 HTML 内嵌，分别用清楚且不互相覆盖的字段表达。
- 保持已有 manifest 的读取兼容；如需更改 schema，采用增量字段或明确的版本升级策略，不悄悄改变旧字段含义。
- 为文件复制失败、重复导出、已有资产、窄日期范围覆盖已有宽范围清单等场景添加回归检查。
- 在不输出完整本地路径、聊天正文或密钥的前提下，让 JSON 操作结果能给出各状态计数及报告文件名。
- 补充第二台设备或另一个账号的文档导出验证记录，以区分匹配逻辑遗漏和源设备没有相应文件这两种情况；继续等待 Issue #11 报告者反馈。

### 验收标准

- 所有格式对同一条消息给出的状态含义一致；复制失败不会仍显示“已导出”。
- 重复运行不会把“本次新写入数”误报为“最终可用数”。
- 局部范围导出不会删除其他范围已记录的媒体条目。
- 自动化测试覆盖故障写入和重复运行；至少一份真实环境验收记录注明平台、客户端版本、成功数量和缺失数量，不包含真实聊天内容或个人路径。

### 可选扩展：离线资料包

统一清单后，可将现有消息导出、媒体资产、版本信息和覆盖摘要封装为可迁移目录或压缩包。第一版应只包含用户选定范围的数据，提供清单校验与离线打开说明；默认不加密格式变更、不上传、不自动同步。该任务应以现有导出能力为基础，避免再实现一套媒体匹配逻辑。

## P1：分批完善 `--json` 运行时错误

### 目标

机器调用时，无论成功还是失败，都能得到稳定的 JSON 结果和可判断的错误码；人类交互模式保持现有行为。

### 建议工作

- 先按命令整理运行时失败场景：未初始化、找不到客户端、数据库不可读、权限不足、外部服务失败、输出文件不可写及用户取消。
- 优先选取无真实账号、密钥和网络依赖的失败场景，补自动化回归；需要本机资源的场景记录为手工验收，不把开发机状态写入 CI 测试。
- 对每个 `--json` 失败分支确认 stdout 只有一个机器可读 JSON 对象；日志和诊断文字进入 stderr，退出码与 `success` 状态一致。
- 复用已有错误码，不为同类问题建立多个同义码；错误消息应可读，但不含数据库路径、密钥、账号标识和正文。
- 逐项处理，不先用全局拦截器改造整个 Commander 出口；`--help`、`--version` 和提示信息必须保持兼容。

### 验收标准

- 被纳入范围的命令在成功、预览和失败三种路径下都有明确 JSON 结构。
- JSON 模式 stdout 不混入进度、彩色文本或普通错误行。
- 每个修复场景至少有一个能够触发该失败的测试；测试不依赖真实本地数据库或个人配置。
- README、操作手册和能力发现输出中的命令说明仍通过仓库的命令面检查。

## P2：提高搜索结果的可解释性

**实测补充（2026-10-15）**：这台机器上按默认窗口建了索引（16,027 条）并跑了真实检索，本节要的几件事因此有了具体读数：

- 重排在这台机器上是**一直不生效**的（Typesafe 返 `HTTP 451: not available in your region`）。这正是本节"执行元信息"
  要解决的问题本身：现在 JSON 里**看不出**降级（没有 `reranked` / `degraded` 字段），终端上也看不见——CLI 不转发
  子进程的 stderr，那行 WARN 只有直接跑 Python 时才有，于是"没报错"会被读成"重排过了"。
- **引用定位已经有了**：`id` 是 `article:<相对路径>` 或聊天消息的 `id` + `time`，能回到本地原记录，且不含绝对路径
  （与本节"不要把完整绝对路径变成默认机器接口"一致）。
- 另量到两件本节没写、但同属可解释性的事：**一次检索约 20 秒**，几乎全花在把 62 MB 的 `vectors.npy` 读进内存
  （没有 mmap）；以及**同一篇文章会因为几个公众号都转载而在结果里重复出现**。两项都还没做。
- **找到一个真洞，已修**：那 10,759 篇日报 md 里含 `## 正文` 的有 **0 篇** —— 取正文的判据从来没匹配上，于是送进
  embedding 的全是 YAML 头（抽样 300 篇：汉字占比中位 0.16）。"文章线只能靠标题排序"的原因在这里，不是截断。
  已按真实结构改（0.16 → 0.80），并留了一条会因"退回老写法"而变红的测试；**索引要 `--full` 重建才生效**
  （增量只嵌新 id —— 这是本轮最容易误判成"已经修好了"的一处）。素材厚度另算：日报 md 只有 259 个汉字，
  正文缓存 2,063、Vault 笔记 422，换不换是个独立取舍。
- **建索引这条路也修了两处**（同一天实测踩出来的）：`--full` 原来只给子进程 5 分钟超时，而全量重建要 20 分钟以上
  —— 那个开关在真实索引上**从来没跑完过**；而且原先是"攒到最后才写"，超时/被杀等于把已经花掉的钱和时间一起丢。
  现在每 100 批落一次盘（先向量后 meta、各走临时文件 + replace），被杀只留一个**有效**的半成品，重跑
  `search-index`（不加 `--full`）从断点续；失败批次（实测有 `IncompleteRead`）不再以全零向量入库（那会让那些 id
  永久占位、再也不会被重嵌），改为在 `embedFailed` 里报数。顺带补了"meta 与向量行数不一致时按少的截断"——
  不补的话越界会被 `search()` 的 `except` 吞成"静默退回关键词"，一次真检索看起来像没命中。

- 本节第 3 条那个**合成评估集仍然没有**：现在的排序判断来自手工试问，不是评估集。这一条不因为索引建好了就算完成。

### 目标

当语义搜索的重排服务不可用或被降级时，调用者能看出本次结果采用了哪条路径；检索结果能定位回原始消息或文章。

### 建议工作

- 为搜索结果的机器输出增加简洁的执行元信息，例如向量检索是否执行、重排是否执行、是否降级及稳定错误原因。
- 保持现有结果字段兼容；执行元信息作为可选字段增加，避免将服务暂时不可用伪装成成功重排。
- 建立不含真实聊天内容的合成评估集，分别检查关键词命中、语义召回、重排和引用定位。
- 在评估集证明收益前，不改变默认重排策略，也不为了得到一个完整索引而默认增加云端调用和费用。
- 当返回引用时，提供足以回到本地原记录的稳定标识和时间信息；不要把完整绝对路径变成默认机器接口。

### 验收标准

- 重排成功与降级时的 JSON 可以区分；终端输出也会说明降级原因。
- 同一合成查询能验证命中、排序和引用对象，不依赖个人语料。
- 额外云端发送仍需遵循现有预览、确认和隐私边界。

## P2：按真实消费者需求扩展只读 MCP

### 目标

让外部本地 Agent 能检查同步覆盖和任务结果，而无需解析 CLI 文本或直接读取状态文件。

### 建议工作

- 先确认至少一个真实下游需要此能力，再将 `sync status`、任务结果或媒体覆盖摘要整理为只读 MCP 资源/工具。
- MCP 与 CLI 共用现有服务层和校验，不另写一套同步状态解析器。
- 为每个请求限制会话范围、时间范围、返回数量及字段；返回中不含密钥、绝对路径和聊天正文，除非具体工具明确提供且受相应确认协议保护。
- 对不完整状态保留 `complete`、`unverified`、`partial` 的区别，不能将“未验证”显示成“完整”。
- 增量游标只有在各相关后端都能验证正确性后，才作为稳定接口开放。当前可继续使用重叠时间窗与本地去重。

### 验收标准

- MCP 与 CLI 对同一同步状态返回一致的覆盖信息。
- 请求上限、未知会话、部分完成、未知 schema 和损坏状态文件均有明确结果。
- 使用合成状态文件完成集成测试；默认能力边界与 `capabilities --json` 一致。

## P3：再评估的平台与 AI 扩展

这些方向需要先有明确用户需求或验证证据，暂不作为近期主线：

- **本地模型：** 先通过能力检测和小规模体验验证基础检索/摘要质量，再考虑统一模型执行层；云端仍是显式配置和显式选择。
- **日报阅读状态：** 如果用户确实需要跨日报恢复进度，再增加本地阅读标记、收藏和笔记关联；先定义可迁移的数据格式和备份方式。
- **客户端兼容矩阵：** 将真实反馈沉淀为版本、平台、数据库类型和媒体覆盖的脱敏验收记录，优先修复高频兼容问题。
- **公开开发接口：** 只有当外部项目确实需要在同一进程内复用能力时，再讨论稳定公共 API。现阶段 CLI/JSON/MCP 已是明确集成面，插件加载器会扩大代码权限范围。

## 明确不作为近期目标

- 未验证的个人微信界面自动化、个人账号自动发信、拉群或群管理。
- 默认云端同步、默认上传聊天数据或无人确认的云端分析。
- 为了“插件生态”直接开放任意进程内代码加载。
- 在各后端未提供可靠依据时承诺稳定消息游标或无遗漏同步。
- 对找不到的图片、文档、语音或视频做猜测性匹配。

## 建议的拆分顺序

| 顺序 | 可独立评审的工作项 | 主要依赖 | 完成信号 |
| --- | --- | --- | --- |
| 1 | 历史回填缓存语义与强制重抓选项 | 当前未提交的缓存改动 | 缓存命中、失败、刷新及日报复用均有测试 |
| 2 | 媒体状态语义统一与复制失败回归 | 现有 manifest 与媒体报告 | 同一文件在报告、清单和导出结果中的状态一致 |
| 3 | 第二环境的文件导出验收 | 可获得的第二账号/设备与授权 | 有可复核的脱敏计数和缺失分类 |
| 4 | JSON 运行时错误分批审计 | 错误码和各命令现有分支 | 每批命令的失败 stdout、stderr、退出码均有测试 |
| 5 | 搜索降级元信息和引用 | 现有搜索结果结构 | 调用者能识别重排未执行并定位来源 |
| 6 | 只读 MCP 同步状态扩展 | 已存在的 sync 状态服务；明确下游需求 | CLI/MCP 一致性与权限测试通过 |
| 7 | 资料包、阅读状态或本地模型试点 | 前序任务的真实使用反馈 | 有可量化需求、预算、边界和回滚方案 |

前三项是建议的下一轮范围。第 3 项依赖外部环境，若暂时没有第二设备，可先完成前两项与 JSON 错误审计，不应将“没有第二台设备”误报成代码验证通过。

## 每项任务的交付清单

每个实现任务在合并前应留下：

- 一个明确的问题描述和用户可见行为变化；
